# RepairProof final release-readiness assessment

**Assessment date:** 23 November 2026  
**Decision:** **NO-GO for production launch**  
**Scope:** Current repository, checked-in release/operations documentation, and local checks run for this assessment, including the blocker corrections recorded on 23 November. No production account, live service, provider configuration, or customer dataset was available. This assessment does not claim a penetration test, privacy-law opinion, WCAG conformance, or a successful deployment.

## Applied corrections in the working tree

- Technician intake now uses one transactional `POST /cases/intake`; the remaining forms call implemented diagnostic, quotation/send, step, test, evidence, status, and warranty routes with server DTO fields. Technician completion still requests verification; only the backend's separate independent-verification record can allow final completion.
- Device listing/read/update/delete now scope technicians to devices they registered or that have a case assigned to them. Case intake also checks active membership and registers the device to the acting profile.
- Authorization responses now use a minimized projection. The token, customer phone/email, device serial/IMEI, address, raw file URLs, and ORM aggregate are not returned. Authorization-token values are also removed from regular case create/list/detail responses. Public authorization routes fail closed unless `CUSTOMER_AUTHORIZATION_ENABLED=true`, which is `false` in checked-in examples; token routes send `Cache-Control: no-store` and `Referrer-Policy: no-referrer`.
- Draft-only operational/legal materials were added: [privacy notice draft](privacy-notice-draft.md), [terms and repair-authorization draft](terms-and-repair-authorization-draft.md), [support and incident runbook](support-and-incident-response.md), and [accessibility release gate](accessibility-release-gate.md). These contain approval requirements/placeholders; they are not ready-to-publish policies or staffed operational coverage.
- These are source changes and local tests. No deploy, legal sign-off, support staffing, provider log redaction, full HTTP/database journey, or assistive-technology evaluation is claimed.

## Features that must remain disabled or explicitly unavailable

1. **Real evidence intake and certificates represented as independently verified:** keep disabled until private object storage, malware scanning, object backup/restore, signed URL projection, full content-integrity checks, and independent-verification workflow pass staging tests. A SHA-256 match shows byte stability, not authenticity or truth.
2. **Customer authorization links and public certificate detail:** API gate `CUSTOMER_AUTHORIZATION_ENABLED` defaults to `false`; keep it false until HTTP contract tests confirm the allowlisted response and headers, proxy/access logs redact path tokens, link revocation/expiry behavior is tested, and privacy/legal owners approve the notice. The old ORM serialization has been removed in source, but this is not yet a release-verified public flow.
3. **Consumer accounts/dashboard/device passport and shop/platform admin workflows:** mark unavailable. The consumer account role/API is not supported; key administration screens are not complete end-to-end.
4. **Invoice OCR:** keep disabled in product flows. FastAPI tests pass, but Nest does not call it; it must never approve quotations or mark extracted fields verified.
5. **LLM explanations:** keep disabled. If later enabled, explanations must remain evidence-cited decision support and must not make truth, fraud, or definitive-diagnosis claims.
6. **General diagnostic consistency claims:** limit to the small, source-reviewed exact rules in the catalog, with human review and displayed limitations. Do not imply broad device/model coverage or photo-only diagnosis verification.
7. **Price benchmark claims:** abstain unless comparable transaction sample thresholds, regional/inflation normalization, explainability and privacy review are satisfied. Never label a quote fraudulent from price deviation.
8. **Email/SMS/WhatsApp, warranty-expiry automation and scheduled jobs:** keep delivery/automatic reminders disabled until provider DNS/credentials, durable scheduling/retry behavior, idempotency, monitoring and customer opt-out/preferences are tested. SMS/WhatsApp are not implemented.
9. **Payments, maps/geolocation, live inventory integration, and unsourced diagnostic rules:** unavailable; do not present controls or claims implying they operate.
10. **All real customer, device, invoice, and repair evidence on the all-free Vercel/Render/Neon demo topology:** prohibited for launch. Use synthetic data only until commercial terms, durability, security and restore requirements are met.

## Release decision

**Production launch is not permitted.** The blocker list must be resolved, each correction verified in a release-candidate environment, and the verification evidence reviewed by release, security, privacy, and operations owners. Passing unit tests, local builds, a mock-backed browser suite, or a green GitHub run alone does not clear deployment, backup, privacy, tenant authorization, or support blockers.

The narrowest honest state today is a **local/demo prototype with explicitly fictional data and unavailable-feature messaging**. No public customer onboarding, real evidence upload, verified-repair claim, or production data migration should occur under this assessment.
